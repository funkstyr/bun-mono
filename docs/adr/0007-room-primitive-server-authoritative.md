# Room primitive: server-authoritative, hono-hosted, with a per-kind reducer

We introduce a generic realtime **Room** primitive — built first for a chat feature (iteration 2) and reused for Royalty multiplayer (iteration 3) — as a server-authoritative actor that lives in `apps/server` (hono on Bun) and stores its state in the existing SQLite database. Clients submit **intents**, the server validates them and emits **events**, and each Room kind plugs in a small reducer that owns its domain-specific validation, state mutation, and payload redaction. The PartyKit standalone runtime is _not_ used; we keep only `partysocket` on the client for its reconnect/queue ergonomics. See `CONTEXT.md` § "Multiplayer & rooms" for the domain language and locked rules.

## Considered Options

- **Pure relay / peer-broadcast** — rejected. Clients would publish facts and the server would just fan them out. Cheap for chat but structurally incompatible with Royalty: you cannot trust a client to declare "I played the 3♣ and won the trick." Adopting it would force a full architectural rewrite in iteration 3 — precisely the rewrite "chat-as-vehicle" was meant to avoid.
- **PartyKit on Cloudflare (standard deployment)** — rejected. Would mean Workers + Durable Objects for the Room runtime, with hono on Bun for the rest of the app. PartyKit gains us free hibernation, edge presence, and per-Room durable storage, but the Room actor would need to call back to hono over HTTP for every membership/auth lookup against SQLite (which is embedded in the Bun process via `@effect/sql-sqlite-bun`). Two deployment targets, a network hop on every connect/auth-check, and a cross-runtime invariant for cache coherence — too much operational weight for a personal-scale project. Revisit if we ever need real edge presence or hibernation at scale.
- **PartyKit's Server class embedded in the Bun process** — rejected. The class is theoretically runtime-portable, but Bun is not a well-trodden host for it; we'd be on our own for any compatibility surprise, and the value over option (c) is marginal — we still hand-write actor lifecycle, just inside someone else's class.
- **Anonymous identity / no auth required for Members** — rejected. A 4-player Royalty session can pause across hours and disconnects; identity-as-socket means a reconnecting Player is a stranger to the Room and cannot reclaim their seat. Stable `userId` from better-auth is the property that makes Royalty multiplayer viable; bolting auth onto a primitive that started anonymous is the most common multiplayer-system regret. **Hybrid** (Members require auth; Spectators are anonymous and uncapped) was the right cut — see `CONTEXT.md` for the resulting Member/Spectator distinction.
- **Request/response over the WebSocket (sync ack-back, then broadcast)** — rejected. Two-phase: server sends `ack` directly to the sender, then broadcasts the public event. For chat it's fine; for Royalty the broadcast already includes the player who made the move, so the ack-back duplicates information and complicates the "sender's event-handler also handles the sender's own actions" property. **Fire-and-forget with `intentId`/`replyTo` correlation + a targeted `intent_rejected` event for failures** collapses the two paths into one: the broadcast IS the ack. Optimistic UI is natural; the same machinery handles chat and game-state reconciliation.
- **One global SQLite table for everything (registry, roster, events, presence)** — rejected. Per-event SQLite writes for high-frequency chat/typing are fine in isolation but unnecessary pressure on the main DB, and presence is intrinsically ephemeral — storing it persistently is busywork. The chosen split keeps each kind of state in the store that fits its access pattern.
- **Per-Room PartyKit storage for the event log** (originally proposed during Q7) — rejected as a consequence of dropping the PartyKit runtime. The same access pattern (per-Room locality, rehydrated on cold-start, capped at the last 500 events) is preserved by a `room_event` table keyed on `(room_id, position)` with a per-Room index, and pruning logic in the actor on each write past the cap.
- **Protocol versioning via a `v` field on the envelope** — rejected for v1. The **Room _kind_** identifier _is_ the version — when chat's protocol evolves incompatibly, it becomes `chat.v2`; old Rooms continue to use `chat.v1`. Migration is per-Room-kind, not global, and adding a `v` field now would invite premature versioning gymnastics.
- **Typing indicators out-of-scope for chat v1** — rejected. Looks like polish, but exercises a _different_ event lane (transient, never stored, broadcast to live connections only) that Royalty's "thinking" / move-preview animations need in iteration 3. Cheaper to bake the **durable vs transient broadcast lanes** into the primitive now than to retrofit later. Edits, deletes, reactions, threads, mentions, and attachments are genuinely cut — none of them exercise a primitive shape Royalty also needs.
- **Public Room list + matchmaking in iteration 2** — rejected. These are not extensions of the primitive; they are application-layer discovery features whose shape differs sharply between chat (Slack-style channel browser) and games (live-games lobby, "find me a seat" matchmaker). Building them for chat first would design them into the wrong shape. Deferred to iteration 3 and scoped to Royalty Rooms specifically.

## Consequences

- **Two new workspace packages.** `packages/room-protocol` — pure arktype schemas for intents and events, no runtime dependencies, depended on by both `apps/server` and `apps/web`. `packages/room-server` — the Room actor base class, lifecycle (cold-start rehydration from SQLite, in-memory presence, hibernation when empty), broadcast fan-out, and the `RoomReducer<TIntent, TEvent, TState>` interface that each Room kind implements. A `chat` reducer ships with iteration 2; a `royalty` reducer is added in iteration 3 and wraps the existing pure-function engine in `packages/royalty`.
- **Three new SQLite tables** managed by Drizzle in `packages/db`: `room` (id, slug, kind, created_by, created_at), `room_member` (room_id, user_id, slot_index, last_seen_at), `room_event` (room_id, position, kind, payload, from_user_id, ts, durable). The event log is capped per Room at 500 rows; older rows are pruned on each write past the cap. Presence is **not** stored — it lives in the actor's in-memory state and is recomputed from active connections.
- **The `partykit` server dependency is unused** and should be removed from `apps/server/package.json` during implementation. `partysocket` on the client stays — its reconnect/backoff/queue behaviour is the part of the ecosystem we actually want, and it works against any WebSocket server.
- **WebSocket auth is cookie-based** on same-origin connections; the server reads the better-auth session cookie on `Upgrade`, looks up the session, and attaches the `userId` to the connection. No-cookie connections become Spectators by default. Mid-session cookie invalidation demotes the connection to Spectator on the next event boundary rather than disconnecting it abruptly.
- **The Member-slot TTL is a _disconnect_ clock**: it runs only while the Member has no active connection. Any active WS connection holds the slot indefinitely. A sweep job (or on-connect lazy check) releases slots whose `last_seen_at` is older than 24h.
- **Iteration 3 (Royalty multiplayer) adds a new Room kind without touching the primitive.** It contributes: a new `royalty` namespace in `room-protocol` (intent and event schemas), a new reducer in `room-server` that wraps the existing engine, a new route `/royalty/m/:slug`, and one new domain rule — Royalty Rooms broadcast a _redacted_ version of the game state to each connection (each Player sees only their own hand). The primitive treats payloads as opaque; redaction is a reducer responsibility.
- **Discovery features (public Room list, matchmaking) are out of scope for iteration 2 and 3 will introduce them only for Royalty Rooms.** A new HTTP endpoint will list public Royalty Rooms with open slots; a matchmaking endpoint will assign a User to one (or spawn a new one) with sensible defaults. The chat Room kind never gets discovery.
- **Operational note:** all Room work runs in the single `apps/server` Bun process alongside the existing hono HTTP/orpc surface and SQLite. There is one deployment, one log stream, one set of OpenTelemetry traces. If we ever need to scale Rooms beyond what one Bun process can handle, the path is to extract a sibling service or revisit PartyKit-on-Cloudflare; the protocol and the reducer interface are deliberately portable enough to make that migration mostly mechanical.
